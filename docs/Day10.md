- [ ] **스트리밍 UI**: Next.js에서 토큰이 실시간으로 흐르는 채팅/결과 화면

- [ ] **에러 처리**: 도구 실패·모델 에러·빈 검색 결과가 나도 앱이 멈추지 않게 처리

## 3. 프로젝트 트랙 — 하나 고르기

관심사에 맞는 걸 고르세요. (직접 아이디어를 내도 좋지만 필수 요건 §2는 지킬 것.)

### 트랙 A — 🔬 연구/논문 어시스턴트 (ML 개발자 추천)
- **데이터**: 관심 분야 논문 PDF 여러 편 (arXiv 등)
- **도구**: `searchPapers`(RAG over PDFs), `arxivLookup`(메타데이터 fetch), `webSearch`(최신 정보), `summarize`
- **에이전트**: "이 논문들에서 X 기법을 비교해줘" → 검색 → 종합 → **출처 인용 리포트**
- **새 기법 후보**: **PDF 로더**(§4-2), **구조화 출력**(리포트 스키마, §4-4)

### 트랙 B — 🗂️ 개인 지식 워커
- **데이터**: 본인 노트/문서/북마크(마크다운)
- **도구**: `searchNotes`(RAG), `getCurrentTime`, `calculate`, (선택) 캘린더/할일 스타일 도구
- **에이전트**: "지난주 회의 노트에서 액션 아이템 뽑아줘" 같은 개인 비서
- **새 기법 후보**: **라우팅 노드**(질문 유형 분기, §4-1), **HITL**(행동 전 승인, §4-3)

### 트랙 C — 💻 코드베이스 Q&A 에이전트
- **데이터**: 특정 GitHub 저장소(소스 파일들)
- **도구**: `searchCode`(RAG over code, 코드용 청킹), `githubUser`/`repoInfo`, `runSnippet`(선택)
- **에이전트**: "이 레포에서 인증은 어떻게 처리해?" → 관련 파일 검색 → 설명 + 파일 인용
- **새 기법 후보**: 코드용 스플리터(`RecursiveCharacterTextSplitter.fromLanguage`), 라우팅 노드

### 트랙 D — 📊 데이터 분석 에이전트
- **데이터**: CSV/표 데이터 + 설명 문서
- **도구**: `queryData`(집계/필터), `describeColumns`, RAG(데이터 사전 검색)
- **에이전트**: "지역별 매출 상위 3개와 추세 알려줘"
- **새 기법 후보**: 구조화 출력(차트용 JSON), 계획 노드

## 4. 캡스톤급 새 기법 (최소 1~2개 도입)

Day 9까지의 "단순 ReAct 루프"를 넘어 아래 중 **프로젝트에 맞는 1~2개**를 도입하세요. 이게 캡스톤을 "그냥 Day 9 복제"가 아니게 만듭니다.

### 4-1. 라우팅/계획 노드 (그래프의 진짜 힘)

**왜**: 모든 질문을 같은 루프로 처리하는 대신, **질문 유형을 먼저 분류**해 다른 경로로 보냅니다. 이게 LangGraph를 쓰는 핵심 이유(단순 체인으론 불가).

📖 설명용 — 라우터를 조건부 엣지로 (설계 힌트)

```ts
// 예: 질문을 "지식 검색형" vs "계산/행동형"으로 나눠 다른 노드로
function routeByIntent(state: typeof MessagesAnnotation.State) {
  const lastUser = /* 마지막 사용자 메시지 텍스트 */ "";
  // 간단히는 키워드/휴리스틱, 정교하게는 작은 LLM 분류 노드로
  if (/논문|문서|Day\d|설명/.test(lastUser)) return "retrieve";
  return "agent";
}

new StateGraph(MessagesAnnotation)
  .addNode("retrieve", retrieveNode)   // RAG 먼저 태우는 경로
  .addNode("agent", callModel)         // 일반 도구 루프
  .addNode("tools", toolNode)
  .addConditionalEdges(START, routeByIntent, ["retrieve", "agent"])
  .addEdge("retrieve", "agent")
  // ... agent ↔ tools 루프는 Day 9와 동일
  .compile();
```

💡 더 정교하게는 **LLM에게 분류를 맡기는 별도 노드**(구조화 출력으로 `{route: "..."}` 반환)를 두세요. 🐍 Python LangGraph의 라우팅 패턴과 동일.

### 4-2. PDF/새 로더 (트랙 A/C 추천)

📖 설명용 — LangChain PDF 로더

```ts
import { PDFLoader } from "@langchain/community/document_loaders/fs/pdf";
// pnpm add pdf-parse 가 필요할 수 있음
const loader = new PDFLoader("papers/attention.pdf");
const docs = await loader.load();   // 페이지별 Document[] (metadata에 page 포함)
// 이후 Day 8의 splitter → embeddings → MemoryVectorStore 파이프라인 그대로
```

💡 로더만 바꾸면 나머지 RAG 파이프라인(Day 8)은 **그대로 씁니다** — "인터페이스 동일"의 이점(Day 8 §4-3).

### 4-3. HITL — 행동 전 사용자 승인 (트랙 B 추천)

**왜**: 에이전트가 "메일 보내기"·"파일 삭제" 같은 **되돌릴 수 없는 행동**을 하기 전, 사람이 확인하게 합니다. 실무 에이전트 안전의 핵심.
- LangGraph는 체크포인팅 기반 HITL을 지원합니다. 그래프 실행을 **중단(interrupt)**했다가 승인 후 재개하는 방식이에요.
- 📖 개념만: 위험한 도구 노드 앞에 "승인 대기" 상태를 두고 UI에서 승인/거절 → 재개. 구현은 LangGraph 문서의 "Human-in-the-loop" 참고.

### 4-4. 구조화된 최종 출력 (트랙 A/D 추천)

**왜**: 자유 텍스트 대신 **정해진 스키마의 리포트/JSON**을 뽑으면 UI에 카드·표로 예쁘게 렌더할 수 있습니다.

📖 설명용 — LangChain 구조화 출력

```ts
import { z } from "zod";
const ReportSchema = z.object({
  summary: z.string(),
  keyPoints: z.array(z.string()),
  sources: z.array(z.string()),
});
const structuredModel = model.withStructuredOutput(ReportSchema);
const report = await structuredModel.invoke("위 근거로 리포트를 작성해줘");
// report는 타입 안전한 객체 (Day 3의 Zod가 여기서 최종 활용)
```

### 4-5. 관측/평가 — LangSmith (선택, 강력 추천)

- `LANGCHAIN_TRACING_V2=true` + `LANGCHAIN_API_KEY` 설정 → 에이전트의 **모든 스텝**이 자동 기록.
- "왜 이 도구를 호출했지?", "어디서 느려졌지?"를 눈으로 봅니다. 🐍 에이전트판 프로파일러/디버거.
- 여유가 있으면 **간단한 평가 세트**(질문 5~10개 + 기대 답)를 만들어 답변 품질을 점검하세요.

## 6. 마일스톤 (권장 순서)

한 번에 다 하려 하지 말고 **작동하는 최소 버전(MVP)부터** 키우세요.

1. **범위 확정 (30분)**: 트랙 선택, 만들 것 1문장, 도구 3개 목록, 데이터 정하기. README 초안.
2. **데이터 & RAG (2~3시간)**: 데이터 수집 → 인덱싱 스크립트 → 검색이 되는지 콘솔에서 확인. (UI 전에!)
3. **에이전트 그래프 (2~3시간)**: 도구 이식 + StateGraph 조립 + **커스텀 노드/분기** 1개. **콘솔 스크립트로** 동작 확인(Day 9 방식).
4. **UI & 스트리밍 (2시간)**: `/api/agent` + 스트리밍 훅 + 화면. 출처 표시.
5. **다듬기 & 평가 (1~2시간)**: 에러 처리, `tsc --noEmit` 0, README 완성, (선택) LangSmith/배포.

⚠️ **가장 흔한 실수**: UI부터 만들려다 시간을 다 씀. **RAG·에이전트 로직을 콘솔에서 먼저 완성**하고 UI는 마지막에(Day 7·9에서 그랬듯).

## 7. 평가 루브릭 (스스로 점검)

각 항목을 정직하게 평가해 보세요. 이게 곧 "내가 뭘 아는가"의 지도입니다.

| 영역 | 미흡 | 양호 | 우수 |
|------|------|------|------|
| **에이전트 설계** | 프리빌트 그대로 | StateGraph + 도구 루프 | 커스텀 노드/라우팅으로 흐름 제어 |
| **도구** | 1~2개, 단조 | 3개, 목적 다양 | 도구 설명이 정확해 호출이 안정적 |
| **RAG** | 검색만 됨 | 출처 표시 | 청킹/데이터에 맞게 튜닝, 근거 정확 |
| **UI/스트리밍** | 정적 응답 | 토큰 스트리밍 | 도구/출처를 보기 좋게 렌더 |
| **코드 품질** | 타입 에러 있음 | `tsc` 0, 모듈 분리 | 에러 처리·재사용성·명확한 구조 |
| **문서** | 없음 | README 있음 | 설계 결정·한계까지 기록 |

💡 **모두 "우수"일 필요 없습니다.** 하나라도 "우수"를 목표로 깊게 파는 게, 전부 얕게 하는 것보다 실력에 남아요.
